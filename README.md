# 算法可视化 · Algo Viz

把排序算法的执行过程变成**看得见的动画**：哪两个元素在比较、哪两个位置被交换、哪些已经排好序，都用颜色和位置变化实时呈现。

纯静态站点，**零依赖、零构建步骤**，克隆下来双击就能跑，推上 GitHub Pages 就能分享给任何人。

![算法可视化界面](docs/screenshot.png)

---

## 这个项目解决什么问题

看伪代码学排序，你看到的是「for i = 0 to n-1」；看动画学排序，你看到的是**数据在动**。后者更容易建立直觉 —— 这是项目的出发点。

同时，它也是一次完整的工程实践：算法逻辑与渲染逻辑**彻底解耦**，新增算法不需要改动任何一行渲染代码。

## 已支持的算法

| 算法 | 时间复杂度 | 空间复杂度 | 稳定性 | 特点 |
|---|---|---|---|---|
| 冒泡排序 | O(n²) | O(1) | 稳定 | 相邻比较，带「本轮无交换则提前结束」优化 |
| 选择排序 | O(n²) | O(1) | 不稳定 | 交换次数最少（最多 n-1 次） |
| 插入排序 | O(n²) | O(1) | 稳定 | 接近有序时极快，数据分布选「接近有序」可看对比 |
| 希尔排序 | O(n^1.3) ~ O(n²) | O(1) | 不稳定 | Knuth 增量序列（1, 4, 13, 40…） |
| 归并排序 | O(n log n) | O(n) | 稳定 | 分治；用「写入」而非「交换」计量 |
| 快速排序 | O(n log n) 平均 | O(log n) | 不稳定 | Lomuto 分区，显式栈避免递归爆栈 |
| 堆排序 | O(n log n) | O(1) | 不稳定 | 建大顶堆 + 反复取堆顶 |

## 核心设计：算法与渲染分离

这是整个项目最重要的设计决策，也是它「可扩展」的原因。

### 唯一的契约：操作序列

算法**不认识 Canvas，不认识 DOM，不知道什么叫颜色**。它只做一件事：算完之后，交出「发生了什么」的流水账。

```js
{ type: 'compare',    indices: [i, j] }        // 比较了下标 i 和 j
{ type: 'swap',       indices: [i, j] }        // 交换了下标 i 和 j
{ type: 'overwrite',  index: i, value: v }     // 把 v 写到了下标 i
{ type: 'markSorted', index: i }               // 下标 i 已就位
```

每个操作还附带一份 `stats` 快照（比较/交换/写入次数），所以播放到任意位置，界面上的数字都是准的。

### 为什么这样设计

```
算法层 (src/algorithms/)  ──产出──▶  操作序列  ──消费──▶  渲染层 (src/render/)
     只关心「算什么」                    纯数据               只关心「怎么画」
```

- **新增算法不用碰渲染代码**：写个函数，`push` 几种操作，注册到 `ALGORITHMS` 就完事。
- **可以任意跳转进度**：操作序列是自包含的，从第 0 步重放到第 k 步，画面和「顺序播放到 k」完全一致。拖动进度条不会失真。
- **可以对比任意算法**：对比功能只需要对同一份数据多调用几次 `run()`，不需要任何额外的可视化代码。
- **可以随时换渲染方式**：想从柱状图换成别的形式？只要新渲染层认识这四种操作即可，算法层一行不改。

### 覆盖（overwrite）为什么必须存在

只用「交换」描述所有排序是行不通的。归并排序的合并过程是把值**写到**目标位置，不是交换。用交换硬凑会让统计数字和动画语义都失真。

所以序列里有 `overwrite`。这也说明契约是按**真实的算法行为**设计的，不是按某一种算法的方便程度设计的。

### 添加一个新算法

在 `src/algorithms/` 下写函数，然后在 `ALGORITHMS` 里注册：

```js
import { Tracer } from './tracer.js';

function mySort(input) {
  const t = new Tracer(input);
  const n = t.array.length;

  for (let i = 0; i < n; i++) {
    for (let j = i + 1; j < n; j++) {
      if (t.greater(i, j)) t.swap(i, j);   // 自动记录比较与交换
    }
    t.markSorted(i);
  }
  return t.result();
}

export const ALGORITHMS = {
  // ...已有算法
  mysort: {
    id: 'mysort',
    name: '我的排序',
    en: 'My Sort',
    complexity: { time: 'O(n²)', space: 'O(1)' },
    stable: false,
    blurb: '一句话说明它在干什么。',
    run: mySort,
  },
};
```

再把 id 加进 `ALGORITHM_ORDER` 数组即可。**渲染层、UI 层、测试代码都不需要改。**

## 目录结构

```
algo-viz/
├── index.html                 # 页面骨架
├── package.json               # 只有脚本，没有依赖
├── src/
│   ├── app.js                 # 入口层：串联 UI ↔ 算法 ↔ 渲染
│   ├── algorithms/
│   │   ├── tracer.js          # 契约定义：操作类型 + Tracer 记录器
│   │   └── index.js           # 七种算法 + 注册表
│   └── render/
│       ├── visualizer.js      # Canvas 柱状图绘制 + 操作序列重放
│       └── player.js          # 播放器：requestAnimationFrame 驱动
├── styles/
│   └── main.css               # 全部样式
└── tests/
    ├── verify.js              # 算法正确性自检（371 次运行）
    ├── dom-integration.js     # 界面集成测试（DOM 桩跑真实 app.js）
    └── serve.js               # 零依赖本地服务器
```

三层职责清晰：**算法层**只产出序列，**渲染层**只播放序列，**入口层**负责把用户操作翻译成调用。

## 测试

### 算法正确性（`tests/verify.js`）

对七种算法跑 **53 个用例 × 7 种算法 = 371 次运行**，每次校验五件事：

1. 不修改调用方传入的数组
2. 结果确实有序
3. 元素守恒（不丢不多）
4. **重放操作序列能得到同样结果** —— 这是渲染层能任意跳转的前提
5. 所有操作下标都在合法范围内

边界用例覆盖空数组、单元素、全相等、已有序、完全逆序、含重复值、含大值，以及 40 组随机数据。

> 这套测试在开发中真的抓到了三个 bug：归并排序比较了正在被覆盖的数组、堆排序的下沉终止条件写反了、空数组时标记了越界下标。这就是为什么要写测试，而不是「跑起来看着对」。

### 界面集成（`tests/dom-integration.js`）

用最小 DOM / Canvas 桩，在 Node 里加载**真实的 `app.js`**（不是复制一份逻辑），验证初始化、播放控制、切换算法、改数据规模、对比模式、统计同步等 30 项断言。

## 部署到 GitHub Pages

项目是纯静态的，**不需要构建步骤**，直接把仓库根目录作为站点发布即可。

### 步骤

1. 在 GitHub 上新建一个仓库（例如 `algo-viz`），**不要**勾选初始化 README。

2. 本地关联并推送：

```bash
git remote add origin https://github.com/<你的用户名>/algo-viz.git
git branch -M main
git push -u origin main
```

3. 打开仓库的 **Settings → Pages**：
   - **Source** 选 `Deploy from a branch`
   - **Branch** 选 `main`，目录选 `/ (root)`
   - 点击 **Save**

4. 等 1～2 分钟，访问：

```
https://<你的用户名>.github.io/algo-viz/
```

### 部署注意事项

- **所有资源路径都必须是相对的**（`./src/app.js`、`./styles/main.css`）。本项目已经全部使用相对路径，所以部署在子路径 `/<仓库名>/` 下也能正常工作。
- 因为用的是原生 ES Modules，**不需要任何打包工具**，也就不存在构建产物和源码不同步的问题。
- 推送后如果页面没更新，强制刷新一下（`Ctrl+F5`）绕过浏览器缓存。

## 使用建议

想直观感受算法差异，试试这几组配置：

- **冒泡 vs 快排，规模拉到 120**：比较次数的差距最震撼（接近 10 倍）。
- **插入排序 + 「接近有序」**：你会看到它几乎瞬间完成，这是它 O(n) 最好情况。
- **快速排序 + 「完全逆序」**：Lomuto 分区在逆序输入上会退化，观察它的比较次数上升。
- **归并排序**：注意它的动画形态和交换类算法完全不同 —— 它在做「写入」而不是「交换」。

---

## 一个诚实的说明：关于统计口径

界面上的**交换次数**不是跨算法比较效率的公平指标，原因有二：

1. 插入排序和希尔排序用「相邻交换」实现，是为了产生连续的位置变化动画（更好看、更好理解）。教科书式的搬移写法交换次数会低得多，但动画会变成「值突然跳过去」。
2. 归并排序不是交换排序，它根本没有交换操作，全部计入**写入**。

所以横向比较时，**比较次数**比交换次数更能反映真实效率。界面上也给出了这段说明，避免误读。

## 后续可以做什么

当前结构留好了扩展位置：

- **新算法**：只需按契约产出操作序列（见上文「添加一个新算法」）。
- **新可视化形式**：路径查找（BFS/DFS/Dijkstra）、树结构（BST 插入/删除、红黑树旋转）、动态规划填表 —— 都是「产出操作序列 + 写一个对应渲染层」的同一套思路。
- **并排对比动画**：现在是对比表，可以改成两个画布同时跑，肉眼直接看谁先完成。
- **自定义数组**：让用户手动输入一组数字。
